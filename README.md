Веб-сервис для просмотра почасового прогноза посадок на трамвайных маршрутах Москвы. Проект состоит из Python/FastAPI API и React/TypeScript интерфейса с картой, фильтрами, графиками и выгрузкой CSV.

## Быстрый старт для жюри

```bash
python -m backend.setup_env          # создаёт локальный .env с логином и хешем пароля
docker compose up --build          # http://localhost:8000  (другой порт: TRAM_PORT=8010 docker compose up)
```

Регистрации нет: доступ выдаётся только по логину и паролю из приватного `.env`. Для сервера пароль задаётся интерактивно командой `python3 -m backend.setup_env --server`; сам пароль не сохраняется, в `.env` записывается только PBKDF2-хеш. Файл `.env` нельзя добавлять в Git.

| Что | Адрес |
|---|---|
| Дашборд: карта, графики, экспорт CSV/XLSX, горизонты «неделя» и «год», коэффициенты, остановки и участки | `http://localhost:8000` |
| Проверка каждого эндпоинта руками (в том числе негативные сценарии) | `http://localhost:8000/#/tester` |
| Интерактивная документация REST API (OpenAPI) | `http://localhost:8000/docs` |
| Точки входа API | `http://localhost:8000/api/v1/...` (перечень ниже) |

Два контейнера: приложение (лимит 2 vCPU / 2 ГБ) и PostgreSQL. PostgreSQL хранит пользователей, хеши паролей, сессии, принятые пакеты валидаций и их почасовые агрегаты; статические исторические метки и геосправочники остаются версионируемыми файлами образа. База не публикует порт наружу. Для подложки карты нужны тайлы OpenStreetMap; веб-шрифт загружается с Google Fonts, а без сети используются системные шрифты. Стек: Python 3.12 / FastAPI (тот же язык, что и ML-контур, без сериализации модели между JVM и Python), React 19 + TypeScript 5, Leaflet, PostgreSQL, Docker Compose. Замеры производительности — ниже.

### Вход и хранение данных

- Открыты только экран входа, `/api/health` и служебная документация. Все API с прогнозами, историей, картой, экспортом, потоком и приёмом валидаций требуют действующую HTTP-only сессию.
- Создания аккаунта в API и интерфейсе нет. Единственный пользователь задаётся переменными `AUTH_USERNAME` и `AUTH_PASSWORD_HASH`; сессии с истечением срока хранятся в PostgreSQL, в базе лежит только SHA-256-отпечаток случайного токена.
- `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`. Ошибочный пароль возвращает общий ответ без раскрытия существования логина.
- `POST /api/ingest/validations` теперь атомарно записывает пакет и агрегаты в PostgreSQL. Повтор пакета идемпотентен, конфликтующий `batch_id` получает `409`. Историю и прогноз сервис пересобирает по ревизии БД, поэтому несколько API-воркеров видят одну запись.
- При прямом запуске тестов без `DATABASE_URL` сохраняется локальный CSV-адаптер. В Compose и серверном стеке PostgreSQL обязателен; API не запускается без заданного хеша пароля.

### Отдельное развёртывание на сервере

`docker-compose.server.yml` запускает приложение и PostgreSQL отдельным Compose-проектом: PostgreSQL и API находятся во внутренней сети, входной прокси подключён к своей выделенной bridge-сети. Сети чужих контейнеров и прокси не подключаются. PostgreSQL и API не публикуют порты на хост. Для сервера:

1. Склонируйте репозиторий в `/opt/hackathon-transport-moskvy`.
2. В этой папке запустите `python3 -m backend.setup_env --server`; мастер интерактивно спросит логин/пароль и создаст файл `.env` с правами `0600`.
3. Запустите `docker compose -p moskvy-tram -f docker-compose.server.yml up -d --build`.
4. Установите ежедневную проверку продления: скопируйте `deploy/systemd/moskvy-tram-cert-renew.service` и `.timer` в `/etc/systemd/system/`, затем выполните `systemctl daemon-reload && systemctl enable --now moskvy-tram-cert-renew.timer`.
5. Публичный HTTPS-вход проекта работает отдельно на корне `https://mos.fotur.tech:8443/`; порт `8443/tcp` должен быть разрешён в firewall. TLS-сертификат выпускается Certbot через HTTP-01 на порту 80. Продление проверяется ежедневным systemd-таймером; при фактическом продлении порт 80 временно освобождается, а Caddy на 80/443 автоматически возвращается.

`AUTH_COOKIE_SECURE=true`, cookie SameSite Strict и HttpOnly. Для смены пароля остановите стек, удалите приватный `.env`, снова запустите мастер и пересоздайте контейнер приложения; старые сессии будут отвергнуты после ротации токена или истечения срока.

## Результат модели

- Прогноз: 1 ноября — 31 декабря 2025, полная сетка **10 маршрутов × 61 день × 24 часа = 14 640 строк**.
- Файл для загрузки: [`submission.csv`](submission.csv), разделитель `;`, UTF-8, поля `route;date;hour;prediction`.
- Метод: обучаемый `HistGradientBoostingRegressor` (scikit-learn) по каждой ячейке `маршрут × дата × час`. Признаки включают маршрут, день недели, час, месяц, тип дня по календарю РФ, годовую сезонность и кросс-проверенный средний профиль `маршрут × день недели × час`. Пропущенные часы в обучении считаются нулями. Код обучения и инференса: [`model/forecast.py`](model/forecast.py) и [`model/forecaster.py`](model/forecaster.py); воспроизводимый результат записывается в [`submission.csv`](submission.csv).
- Скользящая временная проверка без перемешивания дат: score **0,8561** на май–июнь, **0,8391** на июль–август, **0,8596** на сентябрь–октябрь; средний score по трём непересекающимся двухмесячным окнам — **0,8516**. Отдельный октябрьский месяц — **0,9033**. Это внутренние оценки, не гарантия результата на скрытом периоде.
- Предыдущая версия этой ML-модели с квадратичной ошибкой давала на этих окнах **0,8521 / 0,8361 / 0,8585** (среднее **0,8489**), отдельно на октябре **0,8934**. Прежний не обучаемый профиль без калибровки давал среднее **0,8227**.
- По сообщению команды, загрузка **прежнего профильного CSV** 25.09.2026 в 13:12 МСК дала **0,85150**. Текущий ML-файл ещё не оценён на скрытом периоде; результат 0,92–0,95 пока не получен.
- У маршрута 5 в истории нет наблюдений. В прогнозе оставлены нули, как в базовом файле организаторов.

**Как читать оценки.** Среднее **0,8516** рассчитано по трём непересекающимся двухмесячным окнам; отдельная оценка октября **0,9033** благоприятнее и не должна восприниматься как гарантированный результат на скрытом периоде. Подробности и путь к улучшению приведены в разделе «Как можно улучшить WAPE-score».

Пересобрать CSV и повторить бэктест:

```powershell
python model\forecast.py --rolling-backtest
```

Скрипт читает компактные разметки из `dataset\labels`, а не сканирует исходные CSV на 10 ГБ.

### Почему точность пока ниже 0,92

Сравнение рабочей модели с предыдущими параметрами воспроизводится командой `python -m analysis.ml_candidates`. Средний score трёх независимых окон: прежняя версия `HistGradientBoostingRegressor` — 0,8489; текущая модель с абсолютной ошибкой и более глубокими деревьями — **0,8516**. Отдельно проверены LightGBM (лучший вариант 0,8480), CatBoost (0,8353), обучение на имитированных датах прогноза (около 0,82), обучаемые дневные итоги (до 0,841) и признаки недавнего уровня (0,836 на трёх окнах). Последние улучшают октябрь до 0,906, но ухудшают более ранние окна: автоматически переносить их в рабочую модель нельзя.

Основной источник ошибок — изменения режима отдельных маршрутов, которых нельзя узнать только из календаря. Средние посадки маршрута 50 в выходной снизились примерно с 12,3 тыс. в июле–августе до 0,6 тыс. в сентябре–октябре. Модель, обученная только до августа, прогнозировала на сентябрь–октябрь около 9,8 тыс. в выходной; даже обученная до сентября версия прогнозировала на октябрь около 5,5 тыс. при факте 0,8 тыс. Маршрут 7 также снизился летом и восстановился осенью. В комплекте есть только 10 месяцев истории, а справочник содержит 20 примеров записей, не план рейсов на ноябрь–декабрь. Для устойчивого приближения к 0,92 нужны доступные на дату прогноза сведения о плановых рейсах, перекрытиях, ремонтах и изменениях маршрутов; их следует подавать в модель как внешние признаки и проверять на хронологических окнах. Историческую погоду будущих дат использовать в базовом прогнозе нельзя.

## Архитектура

```
 dataset/train.csv, test.csv ──► backend/ingest_raw.py ──► почасовые посадки (сверка с labels/*)
 dataset/labels/*.csv ─────────────────────────────┐
model/forecast.py ──► HistGradientBoosting ──► submission.csv ────┤
 isdayoff.ru, Open-Meteo ─► analysis/external_effects.py ─► artifacts/external/ (календарь, погода, effects.json)
 dataset/spravochniki/*.xlsx, dataset/osm/*.json ─► build_map_data.py ┐► artifacts/routes.geojson ┐
                              └► build_stops.py ──┘► artifacts/stops.json     │
                                                                               ▼
  POST /ingest/validations ─► artifacts/ingested.csv ─► DataStore ─► переобучение ML на истории ─► прогноз незакрытых дат
                                                                               │
  FastAPI (backend/app): routers ─► services ─► DataStore + кэш ответов ◄──────┘
        data · scenarios · ingest · stops · live (SSE)       │
                                                             ▼
                                          React + TypeScript + Leaflet (frontend/dist, тот же порт)
```

| Модуль | Роль |
|---|---|
| [`model/forecaster.py`](model/forecaster.py) | Обучение `HistGradientBoostingRegressor`, признаки календаря/сезонности и выдача прогноза; общий offline/live контур |
| [`model/forecast.py`](model/forecast.py) | Обучение, скользящий бэктест и сборка [`submission.csv`](submission.csv) |
| `backend/app/store.py` | Плотные numpy-кубы; после подтверждения полного дня переобучает модель и пересчитывает прогноз после последнего завершённого дня |
| `backend/app/services/series.py` | Единая выборка и валидация для API и экспорта, кэш готовых ответов |
| `backend/app/services/export.py` | CSV и XLSX с учётом фильтров |
| `backend/app/services/scenarios.py` | Корректирующие коэффициенты (в том числе календарь РФ), годовой горизонт |
| `backend/app/services/external.py`, `analysis/external_effects.py` | Внешние источники: календарь и погода, измеренные эффекты, пресеты коэффициентов; сравнение вариантов на отложенных окнах |
| `backend/app/services/corrections.py`, `regime.py` | Поправки прогноза `calendar`, `regime`, `weather` (слой поверх модели, `submission.csv` не меняется); автоматический поиск сдвигов режима |
| `backend/app/services/live.py`, `routers/live.py` | Поток обновлений `GET /stream` (SSE): событие при каждом приёме данных любым воркером |
| `backend/app/services/ingest.py`, `overlay.py` | Нормализация валидаций, общий файл принятых данных (несколько воркеров) |
| `backend/app/services/stopmodel.py`, `stops.py` | Оценка потока по остановкам и участкам |
| `backend/app/errors.py` | Единый формат ошибок `{detail, code}` на русском |

Каждый принятый пакет сразу обновляет историю и SSE-поток. Если пакет завершает все указанные в нём даты, отправитель ставит `complete: true`: сервис считает остальные часы этих дат нулевыми, переобучает модель и заменяет прогноз после последнего завершённого дня. Неполные дни не выдаются модели как нулевые; их посадки отражены в `ml_model.pending_boardings` до завершения. Даты без пакетов также не добавляются в обучение как нули. `GET /api/v1/health` и SSE `/api/v1/stream` показывают имя/версию модели, число обучающих строк, длительность обучения и число переобучений. Это пакетное переобучение по потоку завершённых дней; estimator scikit-learn сам по себе не реализует `partial_fit`. Состояние сервиса — память процесса плюс общий файл принятых данных, поэтому несколько воркеров в одном контейнере работают без общей БД (воркеры замечают чужую запись по `mtime` файла). Для нескольких контейнеров нужен общий том или внешнее хранилище, см. «Ограничения».

## Локальный запуск на Windows

В корне проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements-dev.txt
cd frontend
npm install
npm run build
cd ..
python backend\build_map_data.py
python -m backend.build_stops
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

На macOS/Linux то же самое: `python3 -m venv .venv && source .venv/bin/activate`, слеши вместо обратных.

Для доступа из локальной сети или публичного сервера используйте `--host 0.0.0.0` только вместе с `INGEST_API_KEY` и настройкой обратного прокси/фаервола.

Откройте `http://localhost:8000` (сборка фронта работает на Node 20+), интерактивная документация API — `http://localhost:8000/docs`. API и собранный интерфейс работают на одном порту. Для разработки фронта с hot reload: `cd frontend && npm run dev`, затем `http://localhost:5173` (адрес бэкенда для прокси — `VITE_API_TARGET`, по умолчанию `http://127.0.0.1:8000`).

Карта использует тайлы OpenStreetMap, поэтому для подложки требуется доступ к интернету. Тесты: `python -m pytest`.

## Страница проверки API

`http://localhost:8000/#/tester` (React, тот же билд) — простой интерфейс, чтобы руками проверить каждую возможность бэкенда: запросы прогноза и истории с графиком и таблицей, скачивание CSV/XLSX, коэффициенты с ползунками и правилом, годовой горизонт, остановки и участки (клик по строке открывает динамику остановки), отправка пакета валидаций и вкладка «Ошибки» — 16 заведомо неверных запросов со сверкой статуса и кода (17 на сервере с ключом приёма: ключ вводится в шапке страницы). У каждого запроса показаны статус, время на клиенте и на сервере и сырой ответ. Основной дашборд остаётся на `/`.

## Docker

Рекомендуемый способ — `docker compose up --build` (см. `docker-compose.yml`: том для принятых данных, лимиты 2 vCPU / 2 ГБ, healthcheck, порт через `TRAM_PORT`, адрес привязки через `TRAM_BIND`). По умолчанию сервис доступен только на этой машине. Для публикации за reverse proxy используйте `TRAM_BIND=127.0.0.1`; для прямого сетевого доступа задайте `TRAM_BIND=0.0.0.0` и обязательно `INGEST_API_KEY=<секретный-ключ>`. Без Compose привязывайте порт к loopback:

```bash
docker build -t moskvy-tram-forecast .
docker run --rm -p 127.0.0.1:8000:8000 moskvy-tram-forecast
```

Образ включает API, React build, компактные разметки, справочные артефакты и прогноз. Исходные `train.csv`/`test.csv` (около 10 ГБ) в образ не входят. Два Uvicorn-воркера. Чтобы принятые через API валидации переживали пересоздание контейнера, смонтируйте том и укажите файл:

```bash
docker run --rm -p 8000:8000 -v tram-data:/data -e INGEST_FILE=/data/ingested.csv moskvy-tram-forecast
```

## API

Основной префикс `/api/v1`; прежние пути `/api/...` работают как алиасы. Ошибки всегда JSON `{"detail": "текст на русском", "code": "..."}`: 400 (дата начала позже конца), 404 (маршрут или остановка не найдены), 422 (неверные параметры, период вне данных, слишком широкий почасовой запрос).

| Метод | Назначение |
|---|---|
| `GET /health` | Состояние, версия, периоды истории и прогноза |
| `GET /routes` | Маршруты и суммы посадок |
| `GET /forecast?start&end&route&granularity=day\|hour\|month&corrections` | Прогноз посадок; `corrections` = `calendar`, `regime`, `weather` через запятую (без параметра это прогноз модели как есть) |
| `GET /history?start&end&route&granularity=day\|hour\|month` | История (включая принятые через API данные) |
| `GET /history/weekday-average?route` | Средние по дням недели, сентябрь–октябрь |
| `GET /export?kind=forecast\|history&format=csv\|xlsx&start&end&route&granularity&corrections` | Выгрузка с учётом фильтров и поправок; XLSX содержит лист «Сводка». `calendar` уже входит в базовую модель и повторно не меняет значения |
| `POST /forecast/adjusted` | Прогноз с коэффициентами: `factors {weather, event, season}` (0,5–1,5), точечные `rules` (период, часы, маршруты, 0,1–3,0) и флаги `calendar`, `regime`, `weather_auto`; ответ содержит `base` и `summary` |
| `GET /regime` | Структурные сдвиги режима «маршрут × день недели», найденные автоматически по истории |
| `GET /stream` | Поток обновлений (Server-Sent Events): событие `update` при подключении и при каждом приёме новых валидаций, в том числе другим воркером; раз в 15 с пульс. Параметр `wait` ограничивает время соединения. Браузерный `EventSource` переподключается сам |
| `GET /dispatch/day?date&route&corrections&capacity&vehicles` | Сводка диспетчера на день: почасовой спрос, пиковые часы, отклонение от обычного дня, горячие участки (оценка) и расчёт нехватки вагонов, если заданы `capacity` (посадок за час на вагон) и `vehicles` (вагонов на линии). По умолчанию с поправками `calendar,regime` |
| `GET /dispatch/savings?route&corrections&threshold&limit` | Дни, где прогноз с поправками ниже прогноза модели не менее чем на `threshold` (по умолчанию 25 %): кандидаты на пересмотр выпуска, с причиной (праздник, сдвиг режима) и суммой разницы |
| `GET /weather?start&end` | Погода по архиву Open-Meteo за период и множитель дня по измеренным эффектам осадков и снегопада |
| `GET /factors` | Границы и ориентиры коэффициентов: измеренные на данных (с 95% ДИ) и экспертные (помечены) |
| `GET /calendar?start&end` | Производственный календарь РФ за 2025 год и поправка на праздничные будни |
| `GET /forecast/year?route&growth` | Годовой горизонт: 2025 (факт + прогноз) и сценарий 2026 |
| `POST /ingest/validations` | Приём пакета сырых валидаций до 100 000 записей, идемпотентно по `batch_id` или содержимому; `complete: true` подтверждает полноту дат пакета и запускает обучение на них; при заданном `INGEST_API_KEY` требует `X-API-Key` |
| `GET /stops?route` | Остановки с координатами, районом, признаком узловой |
| `GET /stops/flow?route&kind&start&end&hour_from&hour_to` | Оценка посадок по остановкам |
| `GET /stops/segments?route&...` | Оценка загрузки участков между остановками, пиковый участок |

`granularity=hour` в `/forecast` и `/history` ограничен 31 днём для всех маршрутов и 92 днями для одного; для `/export` ограничения нет.

### Пайплайн данных

`python -m backend.ingest_raw` читает сырые `train.csv` и `test.csv` чанками (без загрузки 10 ГБ в память), оставляет успешные валидации (`validation_result == 1`), берёт маршрут из `ngpt_route`, час — из `tran_date_time` (`input_date_time` ненадёжен) и агрегирует до маршрут × дата × час. Результат сверяется с `labels_*`: **62,4 млн строк → 57 563 почасовые строки, 0 расхождений**; 562 посадки 2025-11-01 — суточный «хвост» файла за пределами разметки. Тот же код нормализации работает в `POST /ingest/validations`.

### Остановки и участки — оценка, а не измерение

В валидациях нет привязки к остановкам: `place_id` — депо. Поэтому поток маршрута делится между остановками справочника по весам (начальная остановка направления ×2, конечная ×0,15, узловая ×1,5; направления поровну), а загрузка участка считается моделью длины поездки (в среднем 8 остановок, остаток выходит на конечной). Все ответы помечены `estimated: true` и содержат описание метода; веса лежат в `backend/app/config.py` и не калибровались, потому что проверить их нечем. Остановки есть только у маршрутов 1, 5, 7, 11, 12 (у остальных справочник координат не содержит; у маршрута 5 нет истории, значения нулевые).

### Поправки к прогнозу и годовой горизонт

Коэффициенты применяются поверх готового прогноза модели, пересчёт мгновенный (в дашборде: при движении ползунка). Значения погоды и календаря **измерены на данных** (раздел «Внешние источники»); значения для «событий» (крупное мероприятие ×1,15, ремонт ×0,8) экспертные и в интерфейсе помечены как непроверенные.

Опциональные поправки доступны в `/forecast`, `/export` и `POST /forecast/adjusted`; модель и `submission.csv` при этом не меняются:
- `calendar`: праздничные будни уже входят в признаки ML-модели. Флаг API сохранён для совместимости и **не применяет повторный множитель** к текущему прогнозу;
- `regime`: структурные сдвиги «маршрут × день недели», найденные по истории (уровень последних 6 недель к средней за всю историю, порог ×0,7 и ×1,3, праздничные будни не учитываются). Сейчас это маршрут 50 в субботу (×0,06) и воскресенье (×0,08) и маршрут 7 в воскресенье (×0,69);
- `weather`: осадки ≥ 5 мм и снегопад ≥ 2 см умножаются на измеренные коэффициенты 0,935 и 0,933 (8 таких дней в ноябре–декабре). Это **фактическая погода из архива**, а не прогноз погоды: на двухмесячном горизонте погоду предсказать нельзя, а на отложенных периодах её учёт точность не повышает, поэтому она предназначена для сценарного анализа.

«Год» это не прогноз модели: данных за полный год для обучения нет, поэтому 2025 показан как 10 месяцев факта плюс 2 месяца прогноза, а 2026 сценарий по сезонному профилю 2025 без тренда, умноженный на `growth`.

## Обновления в реальном времени

API отдаёт `GET /stream` (Server-Sent Events): событие `update` отправляется при подключении и после каждого приёма новых валидаций, в том числе другим воркером. Пакет с `complete: true` запускает переобучение ML и пересчёт прогноза после последнего завершённого дня. Подключить поток и проверить число переобучений и ожидающих завершения дня посадок можно на странице `/#/tester`, вкладка «Приём данных». Панель `frontend/src/panels/StopsMap.tsx` также умеет подписываться на поток, но в текущей сборке основного дашборда не подключена.

Воркеры друг с другом не общаются: каждый следит за общим файлом принятых данных (период `LIVE_POLL_SECONDS`, по умолчанию 1 с), поэтому событие и переобучение происходят независимо от того, какой процесс принял пакет. Это push по факту прихода данных: организаторы не дают поток «с самих трамваев», данные попадают в сервис через приём пакетов.

## Бизнес-ценность и применение

| Задача диспетчерской службы | Что даёт сервис | Ограничение |
|---|---|---|
| Распределение подвижного состава по маршрутам | Прогноз посадок маршрут × день × час, рейтинг маршрутов, пиковые часы (сводка диспетчера `/dispatch/day`). Если диспетчер задаёт пропускную способность вагона и число вагонов на линии, сервис показывает загрузку по часам и сколько вагонов не хватает или в запасе | Числа вагонов и вместимости в данных нет (в наряде только класс ОБК, БК), поэтому они вводятся вручную; сервис не выбирает их сам |
| Снижение переполнения салонов | Часы пика и их форма, пять самых нагруженных участков маршрута по часам (горячие участки), часы перегрузки при заданных вагонах, сравнение дня с обычным днём недели | Загрузка участков — оценка по эвристике, не измерение |
| Уточнение расписания | Профиль потока по часам для конкретного дня и остановки; влияние праздников (−53 % в праздничный будний день) и осадков (−6,5 %) | Расписание в справочнике — один пример рейса |
| Оптимизация эксплуатации | Список дней с пониженным спросом (`/dispatch/savings`): праздничные будни и маршруты со сдвигом режима, где прогноз с поправками ниже прогноза модели; по ним диспетчер пересматривает выпуск и экономит пробег и энергию | Это оценка по прогнозу, не измеренная экономия; стоимость вагоно-часа сервис не знает |
| Планирование на праздники и сезон | Праздничные дни ноября–декабря учитываются одним переключателем; сценарий «что если» по погоде и событиям с мгновенным пересчётом | Влияние событий не измерено |
| Ежедневная работа с данными | Приём пакетов валидаций через API, переобучение после завершения дня и прогноз на ещё не наступившие даты, выгрузка CSV/XLSX | Завершённый пакет синхронно ждёт обучения |

Результат текущей обучаемой ML-модели на скользящем бэктесте: WAPE-score **0,8561** на мае–июне, **0,8391** на июле–августе и **0,8596** на сентябре–октябре (среднее трёх непересекающихся окон — **0,8516**). Октябрь отдельно даёт 0,9033, но это дополнительный, пересекающийся с последним окном срез. Целевой диапазон 0,92–0,95 пока не достигнут.

Далее приведены результаты прежней профильной модели и её ручных поправок. Это исторические эксперименты и диагностические ориентиры; их оценки нельзя приписывать текущей ML-модели.

Что стоит за числами: диспетчер, не зная о праздниках и режиме маршрута 50, выпустил бы на линию вагоны, которых не требуется, а в часы пика 8, 17 и 18 держит наибольшую часть спроса. Что сервис не знает: стоимость вагоно-часа, реальное число вагонов на линии и фактическую вместимость, поэтому денежный эффект не оценивается.

### Пример работы диспетчера

1. В дашборде панель «Сводка диспетчера на день»: выбираем маршрут 7 и понедельник 10 ноября. Видим 26 372 посадки, пиковые часы 8:00, 17:00 и 18:00 (27 % суток) и самый нагруженный участок направления 1: «Улица Хромова» → «Мосгорсуд».
2. Вводим пропускную способность вагона и число вагонов на линии (значения задаёт диспетчер): таблица показывает загрузку по часам, часы перегрузки и сколько вагонов не хватает.
3. Меняем дату на 3 ноября (праздничный будний день): прогноз с поправкой в 2,15 раза ниже прогноза модели, все часы помечены как ниже обычного дня.
4. Внизу панели список дней с пониженным спросом: по ним пересматривается выпуск (например, маршрут 50 по выходным).

**Что подтверждено, а что нет.** Эффект праздника подтверждён и на отложенных периодах, эффект погоды — только статистически. Сравнение на отложенных окнах (WAPE-score при калибровке модели 1,086; для каждого окна эффекты оценены только по обучающей части):

| Вариант | Сен–окт (без праздников) | Май–июнь (6 праздничных будней) | Май–июнь, только праздничные дни | Октябрь |
|---|---:|---:|---:|---:|
| A. Профиль по дню недели (прежний baseline) | 0,8837 | 0,7877 | **0,000** | 0,8876 |
| B. A + поправка на праздничные будни | 0,8837 | **0,8426** | 0,662 | 0,8876 |
| C. Отдельный профиль праздничных дней | 0,8827 | 0,8257 | 0,794 | 0,8884 |
| D. B + фактическая погода | 0,8816 | 0,8463 | 0,662 | 0,8841 |

- Поправка на праздники **не вредит** там, где праздников нет, и на майских окнах даёт **+5,5 п.п.** Профиль по дню недели на праздничных днях промахивается более чем вдвое.
- Погода даже с **фактическими** значениями точность не повышает (в осенних окнах −0,2…−0,4 п.п.): эффект значим статистически, но мал относительно шума часовых данных 11–12 %. Через два месяца погоду предсказать нельзя, поэтому в базовый прогноз она не входит, а используется как сценарий.
- Прогнозный период 2025-11-01 … 2025-12-31 содержит 3 праздничных будних дня (3.11, 4.11, 31.12). Текущая ML-модель уже снижает прогноз на этих днях примерно вдвое относительно соседних одноимённых будней. Файл `artifacts/submission_calendar_proposal.csv` был создан для прежней профильной модели и **не подходит** для текущего ML-прогноза.
- Оговорки: праздничных дней в истории всего 12 (январь и весна), на 31 декабря эффект может отличаться от новогодних каникул января; сокращённый день 1.11 (рабочая суббота) в истории не встречался и не оценивался; для ноября (ближе к весенним праздникам) оценка −49 % может быть точнее объединённой −53,5 %.

## Как можно улучшить WAPE-score

Эксперименты не меняют модель: `python -m analysis.wape_experiments` (4 отложенных окна, обучение до даты и прогноз на следующие 1–2 месяца) и `python -m analysis.make_candidates` (набор файлов для загрузки в `artifacts/candidates/`).

| Идея | Средний score по 4 окнам (прежний профильный baseline: 0,8168) | Вывод |
|---|---:|---|
| Поправка на праздничные будни | 0,8305 | Для старого профиля повышала оценку на майских праздниках; для текущей ML-модели повторное применение недопустимо |
| Поправка на структурные сдвиги «маршрут × день недели» | окно «октябрь»: +0,8 п.п.; окно «сен–окт»: −2,2 п.п. | С сентября маршрут 50 почти не ходит по выходным (≈700 против ≈11 000 посадок в сутки), маршрут 7 по воскресеньям ≈8 000 против 11–14 тысяч; прежний профильный baseline этого не видел. Срабатывает на трёх ячейках, устойчиво 8 недель. В сервисе включается поправкой `regime`. Рекомендуется проверить скором платформы |
| Калибровка уровнем последних 28 дней вместо константы 1,086 | 0,8412 | Константа 1,086 подобрана на сентябре–октябре (на тесте) и применяется к профилю, который уже включает осень: уровень октября к чистому профилю ×1,044. Влияние ±0,5 п.п., знак заранее неизвестен: подбирать по скору платформы |
| Вес свежих данных, медиана вместо среднего, уровень по маршрутам | 0,8394–0,8427 | Разница в пределах шума окон, приоритета нет |
| Погода (даже фактическая) | не улучшает | Только как сценарий |

Оговорки к историческим экспериментам: 0,8837 относится к самому благоприятному окну старого baseline (константа подобрана на нём же); на окнах май–июнь и июль–август тот вариант даёт 0,7877 и 0,7081. Оценка потолка около 0,925 относится только к профильному подходу и не переносится на ML-модель. Кандидаты из `artifacts/candidates/` также созданы для прежних экспериментов и не являются доказательством качества текущей ML-модели.

### Вторая волна экспериментов: 13 окон, события из открытых источников

`python -m analysis.hypotheses` (13 скользящих окон «обучение до даты → прогноз 61 день», градиентный бустинг подключается при установленном scikit-learn) и `python -m analysis.candidates_v2` (файлы для загрузки в `artifacts/candidates_v2/`). Колонка «лучший масштаб» убирает ошибку уровня и показывает, что даёт сама структура.

| Гипотеза | Среднее по 13 окнам | Лучший масштаб | Вывод |
|---|---:|---:|---|
| Текущая модель (× 1,086) | 0,7998 | 0,8414 | Основа сравнения |
| + профиль праздничных будней отдельно, праздники вне профиля | 0,8330 | 0,8573 | Главный выигрыш: +1,6 п.п. в среднем, на майском окне +4,8 п.п. при лучшем масштабе (0,8300 → 0,8782) |
| + без аномальных маршрут-дней (ремонты, закрытия) | 0,8320 | 0,8584 | +0,1 п.п. |
| + без летних каникул (июнь–август) | 0,8267 | 0,8570 | На окне сентябрь–октябрь +0,9 п.п.: профиль не занижен летом |
| Автоматические сдвиги режима по свежим неделям | 0,8230–0,8264 | 0,8519–0,8564 | Вредят: сдвиги в истории в основном временные (ремонты) и возвращаются |
| Погода (осадки, снег, температура), фактическая | 0,8267–0,8382 | 0,8570–0,8588 | +0,1–0,2 п.п., в пределах шума окон; в кандидаты не входит |
| Градиентный бустинг (Пуассон, календарь, лето) | 0,8502 | 0,8672 | Не лучше профиля на окнах школьного сезона (0,8702 против 0,8705) |
| Смесь 50/50 бустинг и профиль | 0,8412 | 0,8648 | +0,15 п.п., шум |
| Уровень последних 28–84 дней, по маршрутам | 0,8188–0,8293 | 0,8526–0,8569 | Не улучшает |

Потолки на окне сентябрь–октябрь: профиль самого окна (точные средние маршрут × день недели × час) даёт 0,9253, при известных суточных суммах каждого маршрута 0,9403, чисто пуассоновский шум 0,9791. **Поэтому 0,92–0,95 на скрытом периоде недостижимо профильным прогнозом**: это уровень модели, знающей результат заранее. Реальный потолок на скрытых ноябре–декабре около 0,89–0,91.

Что действительно даёт события из открытых источников (ссылки в `analysis/candidates_v2.py`):

- **Ремонт путей в Протопоповском переулке.** С 6 сентября трамвай 50 не ходит по выходным, трамвай 7 ходит короче, срок «до конца осени». В истории режим виден (маршрут 50: 0,06 обычного уровня, маршрут 7: около 0,58), а заранее известный режим на окне сентябрь–октябрь дал бы +1,8 п.п. (0,8906 → 0,9083). В декабре режим может закончиться: варианты `v1` и `v2`.
- **Запуск трамвая 5 (Рижская — Белорусский вокзал) 16 декабря.** В истории маршрута 5 нет, в сетке прогноза он нулевой, а за 16 дней декабря организаторы ожидали около 20 тысяч посадок в сутки. При нуле это 1–2 п.п. ошибки: варианты `v3`–`v5` (5, 10 и 20 тысяч в будни) отличаются только допущением об уровне.
- **Календарь.** 1 ноября (суббота) рабочий день, 3–4 ноября и 31 декабря праздники. Воскресенье 2 ноября внутри блока выходных: в истории аналогичные дни дают около 0,9 обычного.
- **Мероприятия и другие ремонты.** Сигнал массовых мероприятий в 10 месяцах истории вне календаря не найден; ремонты видны как временные сдвиги отдельных маршрутов (март, июль–август, апрель на маршруте 17) и исключаются из профиля. Трамвайный диаметр Т1 (12 ноября) объединяет маршруты 13, 39, 90 и маршрутов нашей сетки не затрагивает.

Пять итоговых вариантов «максимум скора» (`python -m analysis.candidates_v2 --final`, файлы в `artifacts/candidates_v2/final/`): `f1_central` (ремонт 7 и 50 до конца ноября, трамвай 5 с 16.12 около 10 тыс. в будни, декабрь обычный), `f2_repair_dec` (ремонт продолжается в декабре), `f3_r5_20k` (трамвай 5 по прогнозу организаторов), `f4_gbm_blend` (основа 50/50 с бустингом, праздники и 1.11 по профилю), `f5_level_102` (уровень ×1,02). В профиле усечённое среднее 10 %: на 13 окнах +0,08 п.п. при лучшем масштабе, то есть в пределах шума.

Скоры платформы по итоговым вариантам: `f1` 0,88300, `f2` 0,87565, `f3` 0,87324, `f4` 0,88318, `f5` 0,88561. Что из них следует (оценка по разности скоров, не измерение по ячейкам): ремонт маршрутов 7 и 50 к декабрю почти закончился (`f2` хуже `f1` на 0,7 п.п.; истина примерно на 87 % пути от «режим продолжается» к «обычно»); трамвай 5 не выше 10 тыс. в будни (`f3` хуже `f1` на 0,98 п.п., почти на полную разницу файлов); смесь с бустингом ничего не добавила (`f4` ≈ `f1`); общий уровень выше нашего (`f5` лучше `f1` на 0,26 п.п.); суммарные посадки скрытого периода не выше примерно 13,1 млн. Второй раунд (`python -m analysis.candidates_v2 --round2`, `h1`–`h5`) строится от `f5` и `f4` с этими поправками.

Варианты `v0`–`v7` устроены так, чтобы скор платформы (до 24 попыток в сутки, в зачёт лучший) различал допущения: `v0` против `v1` показывает ценность ремонта, `v1` против `v2` его продолжение в декабре, `v3`–`v5` уровень маршрута 5, `v6`–`v7` уровень сети. Решение о загрузке остаётся за ML-участником.

## Область применимости модели

**Область определения.** Прогноз посадок по маршруту, дате и часу на горизонте до двух месяцев вперёд от конца истории для десяти маршрутов 1, 5, 7, 11, 12, 17, 25, 26, 28, 50. Модель обучается на почасовых наблюдениях; календарные признаки и годовая сезонность входят в признаки. Погода, дорожная ситуация и события в обученную модель пока не входят. Маршрут 5 без наблюдений и получает нулевой прогноз.

**Область адаптации.** Для переноса на новые периоды нужны свежие валидации (тот же формат, пайплайн `ingest_raw` / `POST /ingest/validations`), производственный календарь на нужный год (`isdayoff.ru`) и переоценка качества на отложенном временном периоде. Для новых маршрутов нужна история хотя бы за несколько недель (иначе нулевой прогноз, как у маршрута 5) и справочник остановок с координатами для остановочных срезов. Приведённые выше оценки получены на исторических окнах и не являются результатом на скрытом тесте платформы.

## Дополнительные возможности

- Горизонты: день с разбивкой по часам, неделя, год (профиль 2025 и сценарий 2026).
- Экспорт CSV/XLSX с учётом фильтров; XLSX с листом «Сводка».
- Корректирующие коэффициенты (погода, событие, сезон), точечные правила по дням, часам и маршрутам, календарь РФ; мгновенный пересчёт в интерфейсе.
- Остановки и участки: оценка посадок, загрузка участков на карте, динамика остановки по часам и дням.
- Приём валидаций через API (идемпотентно, защита ключом), воспроизводимый пайплайн сырых данных (62,4 млн строк → 57 563 строки, 0 расхождений с разметкой организаторов).
- Единый формат ошибок API на русском, страница проверки с 16 негативными сценариями, 99 автотестов.
- Внешние источники с измеренным эффектом и воспроизводимый расчёт (`analysis/external_effects.py`).

## Ограничения

- Посадки по остановкам и участкам — оценка по эвристике без калибровки (см. выше), только маршруты 1, 5, 7, 11, 12.
- Потоковое переобучение пакетное, после подтверждения полноты дат пакета; для частых завершённых пакетов понадобится очередь/планировщик и фоновый worker, чтобы не удерживать запрос при обучении.
- Принятые данные лежат в файле, общем для воркеров одного контейнера. Горизонтальное масштабирование по контейнерам требует общего тома или БД; без тома данные не переживают пересоздание контейнера.
- Повторная отправка пакета с другим `batch_id` и теми же валидациями задвоит посадки; дедупликация идёт только внутри пакета и по `batch_id`.
- Годовой горизонт — сценарий, а не прогноз модели.
- Коэффициенты (погода, событие, сезон) задаёт пользователь; их значения по умолчанию экспертные.
- Организаторский справочник даёт координаты остановок только для маршрутов 1, 5, 7, 11, 12 — для остальных (17, 25, 26, 28, 50) остановочные срезы по эвристике недоступны. Линии этих маршрутов на основной карте загружаются отдельно из OpenStreetMap (`dataset/osm/tram_routes_extra.json`, лицензия ODbL; см. `build_map_data.py`).
- Справочник «Наряд» содержит 15 строк за один день (8.02.2026), а «Расписание» — один рейс маршрута 1: это примеры структуры, по которым нельзя восстановить выпуск на период прогноза. Число вагонов и вместимость в данных отсутствуют.
- Календарь и погода загружены за 2025 год; на другой год нужно пересчитать `analysis.external_effects`. Эффект праздника оценён по 12 дням, погоды — статистически значим, но не улучшает прогноз на отложенных периодах.
- Значения коэффициентов для «событий» экспертные; влияние транспортной ситуации, ремонтов и открытия маршрутов не измерено.
- Хранилище — файлы и память процесса (без PostgreSQL/ClickHouse), достаточно для текущих объёмов, для роста нужна БД.

## План развития

1. Дополнить календарные признаки предпраздничными днями, добавить прогноз погоды на короткий горизонт и доступные заранее сведения о событиях и изменениях работы маршрутов.
2. Проверить потоковое переобучение на реальных пакетах и отложенных периодах; добавить признаки графика выпуска после получения истории расписаний.
3. Хранилище принятых данных в БД (PostgreSQL/ClickHouse) для горизонтального масштабирования по контейнерам, приём потоком через очередь.
4. Реальная привязка посадок к остановкам по данным телематики (GPS/АСУ ГПТ), калибровка весов остановок и длины поездки.
5. Остановки для маршрутов 17, 25, 26, 28, 50 (линия уже есть из OSM, порядок остановок и координаты для остановочных срезов — нет); данные о ремонтах и открытии маршрутов как внешние признаки.
6. Авторизация и квоты на приём данных, метрики Prometheus, алерты.
